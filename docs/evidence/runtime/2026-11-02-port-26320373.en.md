## Minimal versioned Queue and Spawn readers

Version 1 retains its existing C++ constants and behavior. Historical JSON files are not rewritten. Version 2 reads Queue and Spawn values only from the exact selected build profile. It never inherits V1 defaults. There is no additional defaults file or new profile registry, and CMake remains unchanged.

`entityCommandQueueLayout` carries the original task state, task array/count, queue array/count, task stride, entity-ID counter, active tracking count and exact buffer capacity. The shared tracker continues to use `ecsWriteLayout.changeTrackerContextOffset`. In both new builds, queue records/count are at manager offsets `0x7b9f08`/`0x7b9f10`, active tracking contexts at `0x7bbfc0`, and the existing profile tracker at `0x7bc030`.

`buildingPropSpawnLayout` carries source entity-ID offset 2096 and allocation-failure marker 42. The former source helper used 2088. The current helper adds two instructions in each of four fatal tails. The adapter constructs the complete expected instruction contract from the selected values and remaps branch labels. It still validates every instruction and referenced helper. No function address or arbitrary callback is supplied by these values.

The existing profile reader, typed owner/view transport and two operation consumers implement this path. Existing authority, Scene, lifetime, ownership, exact-code and stable-readback checks remain. Schema, draft generation and format documentation are updated with the same contract. New owner/resource KFC4 drafts use version 2, while the generator continues to remove unverified write contracts. No other native operation or readiness policy is changed.

The server profile retains its baseline's previous fields too: 31 existing leaf changes, comprising 29 numbers including the format version, ID and SHA-256. Its Queue and Spawn values were independently verified against the server EXE, including source helper RVA 6666352 and building helper RVA 2246880. - At 18:34:55 UTC, server placement operation 9 wrote 576 terrain cells and spawned two props. Native live-world verification confirmed both terrain and props. Client operation 16 received the successful P2P placement confirmation and Undo token.

## Why automatic capture did not complete the port

`capture_runtime.ps1` collects evidence rather than producing a complete production profile. The first attempt lacked the native registry verifier, and the function scan then lacked pinned `capstone==5.0.7`. After preparing those tools only in the ignored capture area, the existing reports could be reused. There was no curated catalog for this exact build. Automatic baseline selection requires exactly one same-target profile, so multiple existing profiles supplied no anchor. The draft generator deliberately removes attribute/write contracts, and the generic CLI validator expects the older execution-profile shape. These tools therefore do not perform the requested complete 1:1 owner/resource-profile port automatically.

Issue #79 remains open for independent verification, including the reporter's Proton environment.
