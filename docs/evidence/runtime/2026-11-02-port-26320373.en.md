# Port of the 26082781 profile to client build 26320373 (Enshrouded 1.0.1.0)

Date: 2026-11-02. Status: experiment, ported, not re-derived. This note records how each value of
`modules/game-runtime/profiles/enshrouded/client/26320373.json` was obtained, and what was checked.

## Inputs

| Build | Steam depot manifest | Executable SHA-256 | Source |
| --- | --- | --- | --- |
| 26082781 (1.0.0.3) | 4708593645837114731 | `d64966e2…19817882` | Fetched from Steam with DepotDownloader; identical to the existing profile's `image.sha256`. |
| 26320373 (1.0.1.0) | 6041160459130491470 | `0403981f…9c645513f2a6` | Installed game, 2026-11-02. PE timestamp 1793351710, SizeOfImage 44302336. Both builds are KFC4. |

## Method (read-only, offline)

- **Functions** (`*Rva` in `.text`): the first 24 to 32 bytes of each function in 26082781, with RIP-relative
  displacements and relative branch operands masked, matched exactly once in the new `.text`.
- **Data** (`*Rva` in `.rdata` / `.data`: the root object, the three owner vtables, the thread registry): every
  RIP-relative reference in the old code was found again in the new code (masked window of up to 64 bytes around
  the instruction), and the new instruction's target read there. All references found again agreed (5/5, 1/1,
  1/1, 1/1, 6/6, 3/3, 6/6). The thread registry keeps its internal gaps (lock + 8 = entries, entries + 6144 = count).
- **Service contract items** of `ecs::GameSettings`, which no code references directly: the type record by its
  qualified name and its unchanged 8-byte hash, the registry slot as the one whose next slot names
  `AdminChangeGameSettings` as before, the system descriptor as the one naming `admin_player` and pointing at the
  ported system function.
- **Structure offsets of 4096 or more**: each occurrence as an instruction displacement in the old code was found
  again in the new code and the new displacement read (votes in brackets).

| Field | 26082781 | 26320373 | Votes |
| --- | --- | --- | --- |
| `ownerLayout.controllerPointerOffset` | 217728 | 217760 | 17 / 20 |
| `ecsReadLayout.executionEntityManagerOffset` | 14769600 | 14776768 | 28 / 28 |
| `ecsWriteLayout.executionModeOffset` | 14769608 | 14776776 | 26 / 26 |
| `serviceLayout.systemCountOffset` | 14764584 | 14771752 | 9 / 9 |
| `ecsWriteLayout.changeTrackerContextOffset` | 15450160 | 8110128 | 10 / 10 |
| `resourceLayout.contextItemRegistryOffset` | 15888 | 15904 | 11 / 15 |

The other large offsets kept their value (same count in both executables, or a unanimous vote for the old value).
**Offsets below 4096 were assumed unchanged**: they are too common to count. The runtime's owner, vtable and
registry checks are the guard against a wrong one.

`attributeCalculationModel` is not carried over: it authorizes an exact build's attribute interpreter, which this
port does not re-validate (as `generate-profile` drops it).
